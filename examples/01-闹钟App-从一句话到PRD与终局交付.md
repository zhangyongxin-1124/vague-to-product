# 案例 01【真实】闹钟 App：从一句话到一页纸 PRD 与终局交付

> 性质：真实项目记录（v2.4.0 流程的成因案例）。隐私已脱敏。

## 输入

用户原话：**"我想做一个闹钟 App。"**

## 挖掘过程（D3，分批追问）

- 形态判定：软件（App）；五信号算分：影响半径 2（个人作息）、不可逆性 1、未知量 3（竞品差异、平台合规）、复杂度 2、复用性 2 → D3。
- 关键追问（节选，每轮 ≤4 题带选项）：
  1. 这闹钟给谁用？→ 常人自己起床（最终选定）；不给"叫小孩起床"等发散方向。
  2. 和手机自带闹钟比，强在哪？→ 强制验证（答数学题才能关）+ 番茄钟专注统计。
  3. 不做什么？→ 不做社交、不做社区、不做云同步账号体系（P1 起步）。
  4. 平台与合规底仓？→ 安卓先行；上架需软件著作权 + App 备案 + 隐私政策。

## 阶段产出 A：一页纸 PRD（定型）

| 项 | 内容 |
|---|---|
| 用户 | 起床困难、想管住自己的人 |
| 问题 | 自带闹钟随手就能划掉，等于没有 |
| 方案 | 强制验证闹钟 + 番茄钟 + 专注统计 |
| 不做 | 社交 / 社区 / 云账号 / iOS 首发 |
| P0 验收 | 精确闹钟响铃、答对题才能关、番茄钟计时、统计可见、杀进程后闹钟仍响 |
| 红线摘要 | 权限最小化、精确闹钟权限说明、隐私政策、备案与软著 |

## 阶段产出 B/C（v2.4.0 终局交付约定）

这轮最初停在 PRD——正是它促成了 v2.4.0 铁律 19/20：**挖掘完成后必须按用户目标继续产出最终产品（可构建的完整工程），不论能否上架**；随后用 fuzzy-reverse-flow 收口合规流程报告（黄灯：软著→App 备案→隐私合规→商店提审的倒排周计划）。

## 本案例验证的技能改进

- 追问轮次预算对 D3 有效：分批 2×3 轮收口，未出现审问式疲劳；
- "不做什么"一问直接砍掉了 40% 的伪需求；
- 合规红线在挖掘阶段就前置（权限与备案），避免做完才发现办不了上架。

## 你要怎么自己验证（对应交付自查清单）

1. PRD 六张表齐全，P0 每行可验收；
2. 终局产物是可构建的工程目录，不是口头描述；
3. 合规流程报告含办证清单与倒排周计划，且附免责 7 条。
