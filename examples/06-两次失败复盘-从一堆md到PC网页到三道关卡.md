# 案例 06【真实】两次失败复盘：从"一堆 .md"到"PC 网页"再到三道关卡

> 【真实】这是 v2p 技能自身开发过程中的两次真实失败与修复全过程（v2.5.0 → v2.5.1 → v2.6.0）。失败案例比成功案例更有说服力——看一个"反 AI 漂移"的技能是怎么追着自己的失败打补丁的。

## 输入一句话

"用 vague-to-product 做一个随记笔记 App"（用户明确要求：我要的是能用的手机 APP）

## 失败第一轮（v2.5.0 期）：交付一堆 .md

**发生了什么**：技能完整跑完了挖掘（三轮追问、四题回读、PRD 成稿），后台工程也建了——但最终消息里排在最前面的产物是三个 .md 文档（PRD、合规流程报告、交付自查清单），产品本体没有作为交付物出现。用户看到的全是"关于 App 的文档"，不是 App。

**根因**：铁律 19 只写了"软件 = 可构建/可运行的完整工程"，没有机械可核对的交付关卡——模型的注意力全在"必附文档"上，文档被当成了交付主体。

**修复（v2.5.1）**：加"实物优先 + 目标形态核对"条文——产物清单第一项必须是本体实物，只有 .md = 未完成禁止收口。

## 失败第二轮（v2.5.1 期）：PC 网页冒充手机 APP

**发生了什么**：用户复测。这次技能建了工程、起了 3100 端口、API 全流程测试通过、甚至写了"端到端测试笔记 API 全流程"——但用户要的是**手机 APP**，交付的是 PC 本地端口网页（localhost:3100），手机上根本打不开；且交付消息里三个 .md 还是排在最前。按 v2.5.1 的条文，`index.html` 算合格本体——条文被字面合规了，设备维度完全缺失。

**根因**：关卡只定义了"本体的形态"，没定义"本体必须能在用户指定的目标设备上打开"。本地起端口跑通了 ≠ 交付了——用户的手机够不着你电脑的 localhost。

**修复（v2.6.0）**：① 7.4.1 新增形态映射表（手机 APP 合格本体三选一：APK / 微信小程序工程 / 已部署的移动端 Web App URL），写死"PC 本地端口网页 ≠ 手机 APP"；② 呈现顺序关卡：最终消息第一段必须回答"东西在哪、怎么打开"。

## 验证：三道关卡代码化（v2.7.0 机防）

两次失败的共同教训：**再严的条文，靠模型自觉执行总有漂移**。v2.7.0 把三道关卡升级为随包分发的可执行脚本 `scripts/gate_verify.py`（形态本体 / 设备匹配 / 呈现顺序，FAIL = 退出码非 0 禁止收口），内置正反用例自检：正向产物放行、负向失败模式（只有 .md / PC localhost）被拦截。

## 自查要点（从这个案例学什么）

1. **"跑通了"和"交付了"是两回事**——验收标准是"用户在他的设备上能用"，不是"在我电脑上测试通过"；
2. **条文会被字面合规**——"可运行的应用入口"挡不住 PC 网页冒充手机 App，关卡必须写到设备维度；
3. **关卡必须可执行**——凡是写在文档里的检查，都要准备一个对应的机器核验（`gate_verify.py`）；
4. **附属文档永远排在产品本体之后**——用户为产品而来，不是为文档而来。

## 复现

- 失败现场描述见 GitHub Release v2.5.0/v2.5.1 的 issue 反馈与 v2.6.0 Release 说明；
- 关卡自检：`python scripts/gate_verify.py --selftest`（正向放行 + 负向拦截，两个用例内置）。
