# 模糊需求挖掘与产出生成器（Vague to Product）

> **你给一句模糊的话，我还一个能用的东西。**
> 不限于软件——文档、表格、图形、3D 模型、音视频、资料库、实物方案，同一套挖掘逻辑。

很多人不是没想法，是想法没成形。这个工具不问你"要什么功能"，而是**给你选项让你判断**，然后**按需求的真实分量决定挖多深**，最后直接产出成品。

## 零、使用前提与能力边界（必读）

> 本项目是「本地文件 + Python CLI + 落盘知识库」；**内置一个本地 stdio MCP Server（`scripts/mcp_server.py`，只读工具、无网络监听）**，除此之外**没有任何 HTTP 服务或云端 API**，不存在可供远程调用的地址。**MIT 解决的是「能不能拿去用」，不解决「别人怎么连上」。** 当前版本 **v2.5.0**，配套 fuzzy-reverse-flow **v1.4.0**。

### 0.1 三档能力边界（A / B / C）

| 档位 | 条件 | 能做 | 不能做 |
|---|---|---|---|
| **能力档 A（完整）** | 宿主支持「读文件 + 执行命令」（tool use）：WorkBuddy、Codex CLI、Cursor / Cline / Windsurf / Trae、Claude Code | 全套 CLI（`plan` / `settle` / `change` / `bundle` / `gate` / `use` / `viz` / `spec` / `profile`）；读取 103 条种子规则与 19 条冷启动坑卡，输出带真实红线的联合报告 | — |
| **能力档 B（注入）** | 模型本身不能执行本地命令，但可在本地召回规则后把规则原文注入 API（DeepSeek API 等 OpenAI 兼容端点） | 拿到召回的规则原文，让模型把硬结论写成人话稿 | 模型不跑 CLI、不写知识库、不产生待审区记录、不执行迁移 |
| **能力档 C（降级）** | **网页聊天、手机 App**、纯提示词输入框 | 只拿到方法论提示词（形态判定、五信号深度、六道闸门 / 四步闭环、反模式） | 拿不到规则库、不能引用具体红线或法条、不能沉淀、不能迁移；合规结论只能写成「请人工向官方核实」 |

**网页聊天与手机只能降级到 C 档。** 这不是模型智力问题，是宿主没有「读文件 + 执行命令」能力；把开源可获取误当成服务可调用，是最常见的坑。（本文件「能力档 A/B/C」与 rfe README「快速开始方式 A/B」含义不同，后者指安装方式。）

## 关键差异：深度不是固定的

这是 2.0 的核心。**同一个工具，对不同需求用不同深度。**

| 需求 | 判定深度 | 问几轮 |
|---|---|---|
| "帮我起个文件名" | D0 直达 | 0 轮，直接做 |
| "写一页纸的会议通知" | D1 标准 | 2 轮 |
| "给客户写一份服务方案" | D2 深挖 | 3–5 轮 |
| "要做个涉及收款和分账的平台" | D3 深度 | 5–8 轮 |
| "我有个想法但完全没想清，要卖给别人" | D4 分层 | 8 轮以上，分 3 批 |

深度由 **五个信号** 打分得出（0–10 分）：

```
影响半径   只影响自己 ──→ 影响公众/涉钱/涉法
不可逆性   改起来便宜 ──→ 已发布/已投产/已开模
未知量     很清楚     ──→ 只有感觉
复杂度     单一静态   ──→ 交互系统/多角色
复用性     一次性     ──→ 要给别用/要卖/要维护
```

**为什么这件事重要**：问少了会返工，问多了会被嫌烦。固定三轮两头不讨好。

## 一条命令联合推演（v2.2.0 起，v2.3.0 增强）

```bash
v2p plan -t "我要做一个招聘小程序"
```

这一条命令会：判定形态与深度 → 给出第一轮 4 个追问 → **静默调用 fuzzy-reverse-flow** 召回合规红线、资源底线、历史坑预警 → 生成倒排里程碑骨架 → 输出统一报告 + 含「合规闸门」的核查卡。你不需要知道 rfe 的存在；想单独做可行性评估时，仍可直接 `rfe recall -q "招聘"`（两套工具独立可用，只是多了一条联合路径）。

交付收尾是强制的：`v2p settle pitfall/rule`（先入待审区，`rfe pitfall approve` 转正）→ `v2p settle done`。没沉淀过任何经验就标记交付，`v2p spec check` 会拦下你。需求变了：`v2p change -t "改了什么"`，自动重跑红线 diff 与工期推演。

其他：`v2p use 项目名`（口味档案按项目隔离）、`v2p gate manual`（手测清单+截图留痕校验）、`v2p bundle --items app,doc,sheet`（多产物一致性对账）、`v2p viz depth / gates / heatmap`（雷达图 / 闸门分布 / 五信号热力图，v2.3.0 新增 heatmap）。

> 完整免责声明见 0.3 节 7 条（报告尾部强制附带）；此处不再使用简版免责。

## 终局交付：先产出最终产品，再合规收口（v2.4.0 新增）

**真实失败案例**：用户说"我想做一个闹钟 app"，D3 挖了 3 轮、交付一页纸 PRD 后流程即停——用户拿到的是需求文档，不是闹钟 app。

v2.4.0 用两条铁律堵死这个口子（SKILL.md 铁律 19/20）：

1. **挖掘的终点是产品，不是文档**。回读确认通过后必须按用户目标产出**最终产品**（软件=可构建/可运行的完整工程，文档=成稿，表格=成品表……八形态各有最低完成定义）。**不论合规结论是绿、黄还是红牌都要交**：绿灯直接交；黄灯照交、红线写成"上架/经营前必须办理清单"；红牌交付"合法改造路线"版本。唯一例外：用户明确说"本轮只要方案"。
2. **交付必附合规流程报告（阶段产出 C）**。用 fuzzy-reverse-flow 收口：结论档位 + 已触发红线（RFE-RL 编码）+ 办什么证 + **倒排周计划**——让用户拿到产品的同时，明确"后续怎么走、怎么安排"。

```
阶段产出 A = PRD / 定型卡（里程碑，不是终点）
阶段产出 B = 最终产品（必交，不论可否上架）
阶段产出 C = 合规流程报告（必附，倒排周计划）
```

> 规范：[`references/final-delivery.md`](references/final-delivery.md) ｜ 报告骨架：[`assets/templates/合规流程报告.md`](assets/templates/合规流程报告.md)

## 用起来

### 对话中

> 我想做个帮老人找零工的 App

它会先说：形态判定、深度初判、三处歧义 + 默认假设，然后一次问 4 个带选项的问题。

### 命令行

```bash
v2p route -t "我想做一份给投资人的商业计划书"   # 判形态 + 算深度 + 给第一轮问题
v2p depth --impact 2 --reversi 0 --unknown 1 --complex 0 --reuse 1
v2p ask --form doc --depth D2 --round 2 --done goal,scene
v2p forms                                    # 看八类形态与必挖点
v2p spec new --title "XX" --brief            # 通用产出定型卡（非软件）
v2p spec check --file XX.md                  # 能不能交付
v2p profile depth D2                         # 记住深度习惯

# 交付质量闸门
v2p gate card -f app -d D2 -o 核查卡.md       # 生成填空式核查卡
v2p gate list -f doc                         # 文档只出 12 项
v2p gate redteam -f app                      # 12 步破坏性测试
v2p gate scan -p ./项目                       # 静态筛查（筛子，非判据）
```

`v2p route` 实际输出：

```
【形态判定】文档与报告（doc）　置信：高　命中：计划书、商业计划
【初判深度】D2 深挖（4/10）
  影响半径 ██ 2　影响公众 / 涉及钱 / 涉及法律
  复杂度   ·· 0　单一静态产出
【轮次预算】3–5 轮，每轮 ≤4 题
【覆盖预演】必挖的 3 个维度中覆盖 3 个　✓
【第一轮先问这 4 个】…
```

## 三个设计要点

**1. 只问能被判断的问题**
"你觉得这个设计好吗"——用户答不出。"这两版你选哪个"——他立刻能答。所以每题都是选项，不是填空。

**2. 每题都标代价**
选项后面写"要 3 天""要资质""省掉登录"，让选择基于真实成本，而不是感觉。

**3. 必须产出"不做什么"**
只说要做什么的规格是废纸。软件的 P0 超过 5 个、非软件的"不做什么"为空，`spec check` 会直接拦下。

## spec check 检查什么

两套标准，自动识别：

```bash
$ v2p spec check --file prd.md            # 软件 PRD
[错误]
  ✗ P0 有 7 个，超过上限 5 个——说明没有 MVP
  ✗ 「不做清单」是空的或只有占位

$ v2p spec check --file brief.md --form doc   # 非软件定型卡
[错误]
  ✗ 「必须包含的内容」太短——没有内容清单，产出必然缺项
  ✗ 「不做什么」是空的
[提醒]
  ! 没看到「当……应……」格式的验收标准
```

**软件看 P0 数量，非软件看内容清单**——用错标准会得到假验收。

## 交付质量闸门（治"看着像 AI 做的"）

需求挖对了、东西也做出来了，还是一眼看出业余——问题几乎总在同一处：**只覆盖了正常路径，剩下的空态、错态、边界、并发、权限全在裸奔。**

所以闸门是**两段式**，不是交付后的清单：

**第一段：动手前先填状态矩阵**

| 情况 | 用户看到什么 |
|---|---|
| 加载中 / 没有数据 / 出错 / 成功 / 不可用 / 极端量 / 素材缺失 | 七行各写一句具体的话 |

填不出来的那一行，就是还没挖到的需求——回阶段二补，不许"到时候再说"。

**第二段：交付前过六道闸门**

| 闸门 | 治什么病 | 项数（软件） |
|---|---|---|
| 完整态 | 点了没反应、列表空白、报 undefined、保存没提示 | 13 |
| 交互 | 浮层被遮、背景乱滚、返回丢筛选、连点发三次 | 8 |
| 布局 | 手机横滚、长标题撑爆、深色看不见字 | 12 |
| 数据 | 假姓名假手机号、字段 undefined、差 8 小时、金额算错 | 12 |
| 工程 | 密钥写前端、构建失败、内存上涨、一错全白 | 11 |
| 可维护 | 调不存在的接口、同类两套写法、改坏回不去 | 9 |

共 65 项（软件 48 项 + 六个非软件形态的等价检查）。每项都写清 **问什么 / 怎么验 / 怎么修**。

**按形态裁剪**：文档不会被问"加载态"，3D 不会被问"滚动穿透"。
**按深度裁剪**：D0/D1 只查核心 7 项，D2 查全部阻断项，D3+ 全量。一张通知不会被 48 项吓退。

**通过标准是可数的**：

```
阻断项未通过 = 0
提醒项未通过 ≤ 3，且每条写清为什么不修
```

**静态扫描只是筛子**，不是判据：

```bash
$ v2p gate scan -p ./我的项目
阻断（2）：  [QGS-01] 疑似密钥明文 / [QGS-02] 疑似写死的假数据
阻断（1）：  列表渲染了，但没有任何空态/加载态处理
提醒（3）：  z-index 9999 / 字符串解析日期 / 调试输出残留
结论：未通过（阻断 3 / 提醒 3）
```

它扫不出运行时才出现的竞态、内存泄漏、层级冲突，也接受误报。**判据永远是 `redteam` 那 12 步真的点一遍。**

## 附录 A · 知识库分层、待审区与版本迁移（v1.3.0 机制）

| 层 | 路径 | 权限 |
|---|---|---|
| **只读种子库** | `<技能目录>/kb_seed/*.json`（103 条规则 / 13 领域） | 随仓库分发，**任何命令都不写入** |
| **可写本地库** | `RFE_KB`，默认 `~/.workbuddy/reverse-engine` | `rules.jsonl` / `pitfalls.jsonl` / `pending.jsonl` / `rejected.jsonl` / `kb_meta.json` |

- WorkBuddy 与 Codex 等**多宿主共用同一份可写本地库**，故新沉淀一律先进 `pending.jsonl` 待审区，人工 `rfe pitfall approve --id` / `reject --id` 后才转正，防止多宿主并行写入污染知识库。
- 结构版本写入 `kb_meta.json` 的 `schema_version=2`（当前目标 **v2**）：v0 = v1.1.x 及更早（无元数据）；v1 = v1.2.0（三件套 + 复核时间戳）；v2 = v1.3.0（字段规范化、fingerprint 去重、季度复核分级、只读/可写库显式分层）。
- `rfe migrate --check` 只报告不写入；`rfe migrate` 执行迁移并自动备份为 `*.backup-v<旧版本>-<日期>.jsonl`，**只改结构不改语义**（补 `created_at` / `source` / `status` / `review` / `schema` / `severity` / `type` / `hit_count` / `verified_at`、规范化 ID、重算 fingerprint、按 fingerprint 去重）。
- 标准顺序：`rfe init` → `rfe migrate --check` → `rfe migrate` → `rfe doctor` → `rfe stats`。
- **环境变量与默认参数**（写代码 / 改配置以此为准）：`RFE_KB`（可写本地库，默认 `~/.workbuddy/reverse-engine`）、`RFE_SCRIPT`（v2p bridge 显式指定 rfe.py）、`V2P_HOME`（口味档案与 plans/ 报告，默认 `~/.workbuddy/v2p`）、`V2P_PROJECT`（多项目口味隔离）。完整清单见 `使用说明.txt` 第 2 节。

## 附录 B · 统一问题编码（消除两套工具告警重复）

| 前缀 | 所属 | 含义 | 全局编码示例 |
|---|---|---|---|
| `V2P-QG-*` | v2p | 交付质量闸门检查项（原短码 `QG-xxx`，等价全称 `V2P-QG-xxx`） | `V2P-QG-101` |
| `V2P-OR-*` | v2p | 编排层冲突 / 状态告警 | `V2P-OR-001` |
| `RFE-RL-*` | rfe | 规则库红线与阻断规则 | `RFE-RL-RULE-ECOM-0001` |
| `RFE-PT-*` | rfe | 踩坑记忆（坑卡） | `RFE-PT-PIT-0001` |
| `RFE-DR-*` | rfe | 知识库自检诊断 | `RFE-DR-001` |

四条硬规则：① 前缀全局唯一；② 编码幂等（已带前缀不再叠加）；③ 同一编码可跨节引用，但按报告末尾「问题编码索引（去重）」计数，红线节与资源底线节按编码集合去重过滤；④ `v2p gate` 仍输出短码 `QG-xxx`（自测依赖），报告引用时用全称。完整规范见 [`references/issue-codes.md`](references/issue-codes.md)。

固定诊断码：`RFE-DR-001` 重复 ID、`RFE-DR-002` 缺 `rule` 字段、`RFE-DR-003` 缺 fingerprint、`RFE-DR-101` 季度复核到期（91-180 天）、`RFE-DR-102` 过期规则（>180 天或无核实日期）。

## 附录 C · 长期维护：季度复核机制

1. 每季度人工核对官方入口后执行 `rfe meta --set-review --note "..."` 记录复核日期。
2. `rfe doctor` 分级标记：91-180 天未核实 → `RFE-DR-101`；超过 180 天或无核实日期 → `RFE-DR-102`。
3. 逐条核实后执行 `rfe verify --id <ID> --confidence high`。
4. 每份输出报告强制附带知识库复核时间戳与 0.3 节完整免责声明。
5. 推广路径固定为：**自用提效 → GitHub 开源 Release**；拦截公开 SaaS，明确禁止公开 SaaS 产品化。

## 附录 D · GitHub Release 部署与发版校验

1. 从 GitHub Release 下载 `vague-to-product-v2.5.0.zip`，核对页面给出的 **SHA256**。
2. 解压到 `~/.workbuddy/skills/<技能名>/`（WorkBuddy）或 `~/.codex/skills/<技能名>/`（Codex CLI）；fuzzy-reverse-flow-v1.4.0.zip 需同级放置（或用 `RFE_SCRIPT` 指定）。
