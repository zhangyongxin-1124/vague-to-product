# 统一问题编码规范（v1.0）

> 适用：`vague-to-product` × `fuzzy-reverse-flow` 联合推演（`v2p plan`）及各自独立运行。
> 目的：消除两套工具在同一份报告里的告警重复与同码不同义。

## 一、为什么需要

`v2p plan` 会同时输出四类告警：质量闸门检查项、合规红线、踩坑记忆、知识库自检诊断。
若各用各的短码（`QG-101`、`RULE-ECOM-0001`、`[!]` …），会出现两个问题：

1. **同码不同义**：不同来源的 `001` 无法判断属于哪个工具；
2. **重复告警**：同一条红线在「合规排雷」「资源底线」「倒排里程碑」三节反复出现，读者难以判断到底有几个独立问题。

本规范给每类问题分配**全局唯一前缀**，并规定「同一编码可引用、不重复计数」。

## 二、前缀表

| 前缀 | 所属工具 | 含义 | 原短码 | 全局编码示例 |
|---|---|---|---|---|
| `V2P-QG` | v2p | 交付质量闸门检查项（65 项） | `QG-101` | `V2P-QG-101` |
| `V2P-OR` | v2p | 编排层冲突 / 状态告警 | 无 | `V2P-OR-001` |
| `RFE-RL` | rfe | 规则库红线与阻断规则 | `RULE-ECOM-0001` | `RFE-RL-RULE-ECOM-0001` |
| `RFE-PT` | rfe | 踩坑记忆（坑卡） | `PIT-0001` | `RFE-PT-PIT-0001` |
| `RFE-DR` | rfe | 知识库自检诊断 | `[!]` / `[~]` | `RFE-DR-001` |

## 三、固定诊断码（RFE-DR）

| 编码 | 含义 | 处理建议 |
|---|---|---|
| `RFE-DR-001` | 规则库存在重复 ID | 合并或重编号 |
| `RFE-DR-002` | 规则缺少 `rule` 字段 | 补全或删除 |
| `RFE-DR-003` | 规则缺少 `fingerprint` | 执行 `rfe migrate` 重算 |
| `RFE-DR-101` | 季度复核到期（91–180 天未核实） | 安排本季度人工复核后 `rfe meta --set-review` |
| `RFE-DR-102` | 过期规则（无核实日期或超 180 天） | 逐条核对官方入口后 `rfe verify --id <ID> --confidence high` |

## 四、四条硬规则

1. **全局唯一**：前缀不重叠；同一问题在任何报告节、任何工具里编码一致。
2. **幂等**：已带 `V2P-` / `RFE-` 前缀的编码原样返回，不再叠加前缀（由 `orchestrate.py::issue_code()` 保证）。
3. **只引用不重复计数**：同一编码可在红线节、资源底线节、倒排里程碑节重复引用；独立问题数量以报告末尾「问题编码索引（去重）」为准。红线节与资源底线节之间用编码集合做去重过滤。
4. **向后兼容**：`v2p gate card/list` 仍输出短码 `QG-xxx`（自测与既有脚本依赖），其全局等价编码为 `V2P-QG-xxx`；报告与文档引用时使用全称。

## 五、落地位置

| 内容 | 文件 |
|---|---|
| 前缀常量 | `vague-to-product/scripts/bridge.py` → `ISSUE_PREFIX` |
| 编码函数 | `vague-to-product/scripts/orchestrate.py` → `issue_code()` |
| 报告头部声明 + 尾部去重索引 | `v2p plan` 生成的 `report.md` |
| 诊断码输出 | `fuzzy-reverse-flow/scripts/rfe.py` → `cmd_doctor()` |
| 自测覆盖 | 两仓库 `scripts/selftest.py` |

## 六、新增前缀的流程

1. 在本表登记前缀、含义与示例，确认不与既有前缀冲突；
2. 在 `bridge.py::ISSUE_PREFIX` 增加映射；
3. 在 `selftest.py` 增加一条「编码不重复」断言；
4. 同步更新两仓库 README 的「统一问题编码」小节与 `使用说明.txt`。
