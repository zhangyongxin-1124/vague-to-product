# 阶段二 · 追问挖掘（维度轮盘，非固定轮次）

> 目的：把「我以为你要的」变成「你确实要的」。
> **轮次由深度决定（见 `depth-governor.md`），每轮从 8 个维度里挑，不按固定顺序。**

---

## 1. 为什么不能固定三轮

旧做法：定位 → 场景 → 边界，永远三轮。问题有三个：

1. **对简单需求是浪费**。用户只是要改个文件名，问 12 个问题会让他觉得你不会做。
2. **对复杂需求是失职**。一个涉及资金结算的平台，三轮问到的东西不足以开工。
3. **对所有形态都用同一套**。文档不需要问「核心动作」，3D 不需要问「要不要登录」——问错了维度，答案是废的。

**改法**：把「轮次」换成「维度覆盖率」。问几轮不重要，问到该问的才重要。

---

## 2. 八个维度（轮盘，可插拔）

| 维度 | 要挖出什么 | 典型问题 | 问到就算够 |
|---|---|---|---|
| **目标** goal | 拿它干什么、为什么现在做 | 「做出来第一件事拿它干嘛？」 | 能说出一个具体用途，不是「有用」 |
| **场景** scene | 什么时候、在哪里、多久一次 | 「上一次遇到是什么时候？」 | 说得出具体某天、具体动作 |
| **对象** object | 内容/功能的粒度与边界 | 「这张表一行代表什么？」「核心动作是哪个？」 | 粒度可数、可命名 |
| **约束** constraint | 钱/时间/人/工具/硬指标 | 「什么时候必须拿到？」「有没有必须遵守的模板？」 | 至少一个硬约束（时间或格式或预算） |
| **质量** quality | 什么算好、什么算能交 | 「什么算过关？」 | 有一个可被第三人判断的标准 |
| **边界** boundary | 明确不做什么 | 「哪些你明确不要？」 | 至少一条「不做」 |
| **交付** delivery | 给谁、什么形式、怎么用 | 「最终以什么形式交？」 | 形式 + 接收者可确定 |
| **演化** evolution | 以后谁维护、会不会扩 | 「以后会不会加人/加数据？」 | 知道是「一次性」还是「要养」 |

### 维度不是问卷，是轮盘

- 每轮从**未饱和的维度**里挑 2–4 个，凑成一轮的题
- **同一维度一轮内不超过 2 题**（超过就是审问）
- **连续两轮不得重复同一维度**（重复 = 没听懂他的答案）
- 该形态的**必挖维度永远优先**（见 `output-forms.md`）

### 各深度的典型覆盖路径

| 深度 | 轮次 | 覆盖维度 | 适合 |
|---|---|---|---|
| D1 | 2 | 目标 + 场景 + 交付 + 约束 → 对象 + 质量 + 边界 | 自用、单一形态、改起来便宜 |
| D2 | 3–5 | 上面 + 约束细化 + 演化 | 要交给别人、有多约束 |
| D3 | 5–8 | 上面 + 逐个风险项 + 维护责任 | 涉钱、涉合规、要长期用 |
| D4 | 8–∞（分批） | 全部，且回到已答维度做「压力测试」 | 用户完全没想清 + 高风险 |

## 3. 三轮的原始设计（保留，作为 D1/D2 的默认骨架）

固定三轮不是错，只是不能**只有**三轮。当深度落在 D1/D2 时，就按这个骨架走：

### 第一轮 · 定位

1. **用途**：做出来第一件事拿它干嘛？（自己用 / 给具体的人 / 给客户 / 卖 / 存档）
2. **替代**：现在怎么解决的？（手动 / Excel / 别的软件 / 不做 / 这是全新的）
3. **交付**：最终交给谁、以什么方式交？
4. **时限**：什么时候必须拿到？

> 这四个答完，形态与分量基本能定。**注意：这一轮不问形态相关的问题**，先定"给谁、要多久"。

### 第二轮 · 对象与质量（这轮决定做得准不准）

- **行为回溯（最重要）**：「上一次你遇到这个麻烦，具体哪天？点了几步、卡在哪、最后怎么解决的？」
- **对象粒度**：该形态的核心粒度问题（表的一行 / 软件的核心动作 / 文档的读者决定 / 3D 的用途）
- **最痛点排序**：慢 / 乱 / 容易错 / 拿不出去，选一个最不能忍
- **失败预演**：「什么情况下你会说这东西没用？」

### 第三轮 · 边界与收敛

- **不做清单**（必须）
- 谁不能用
- 怎么算成功
- 交付形态确认

> D2 以上，第四轮开始进入**约束细化**（模板、口径、合规、数据量级、维护责任）。
> 这些问完还没完，说明是 D3/D4，继续按维度轮盘排。

## 4. 5 Why：穿透表层诉求

用户说的第一层，几乎都不是真需求。

```
用户：我要加个会员体系
Why1：为什么要会员？→ 想区分老客户和新客户
Why2：区分了做什么？→ 给老客户优惠
Why3：为什么要给优惠？→ 他们复购多，我想留住
Why4：不留会怎样？→ 会跑去别家
Why5：他们为什么跑？→ 因为价格差不多，我们没别的差别

→ 真需求：不是会员体系，是「让老客户感知到被区别对待」。
  解法可能是一张手写卡片，成本 0，比会员系统有效。
```

**规则**：连续 3 个 Why 之后，如果答案还在「功能层」，说明问错方向，改用行为回溯。

**但别滥用**：5 Why 只对「表层方案型诉求」有效。用户说「我想要张 A3 海报」，直接问用途就行，追 5 层会被当成抬杠。

## 5. 类比锚定：用已有东西当坐标

用户对「我想要什么」说不清，但说「像什么但不一样」非常准。

句式：**「像 <熟悉的东西> 的 <某个部分>，但 <不同点>」**

| 说法 | 含义 |
|---|---|
| 「像微信的收藏，但能自动分类」 | 结构照收藏，重点在分类 |
| 「像 Excel，但不用学公式」 | 要表格能力 + 自然语言 |
| 「像大众点评，但只有我们园区的店」 | 缩小范围，其余照抄 |
| 「像纸质记账本，但能算总和」 | 极简 + 一个计算 |
| 「像宜家的说明书，但只有一页」 | 图解优先，砍文字 |

**作用**：一句话锁定信息架构、交互习惯、视觉预期，省掉 20 个问题。适用于所有形态——不只是软件。

## 6. 选项生成六原则

1. **互斥且穷尽**，最后留「都不是」
2. **具体到能想象**：「3 步完成，不用注册」而非「效率高」
3. **带代价标签**：要几天 / 要多少钱 / 要什么资质 / 要重做几次
4. **必有一个推荐**，并说明为什么（基于他的约束，不是你的偏好）
5. **允许自由填**：真实需求常在第 5 个选项
6. **选项数量 3–5 个**，超过 6 个他会随便点

---

## 7. 什么时候停（详见 depth-governor 第 4 节）

一句话版：**问到的答案不再改变产出时，就停。**

三个具体信号：
1. 本轮新约束 < 2 条
2. 必挖维度已覆盖
3. 用户回答变短、出现「你看着办」

停之前必须做一件事：**把没问到的写成「默认假设清单」**，交付时显式说出来。

---

## 8. 复合需求：拆，不要塞

如果按该深度的轮次预算问完仍然模糊，先判断是不是**两个需求**：

| 症状 | 判断 |
|---|---|
| 用户说的人群有两类，且行为完全不同 | 拆成两个产品 |
| 用户说「既要有要还要」，且互斥 | 拆成两期 |
| 一个需求里同时有「对内」和「对外」 | 拆成内部版 + 对外版 |
| 用户反复改口，且每次改的是"这是给谁用的" | 拆成两个方向，让他选一个先做 |

**拆的标准**：能各自写出一句话 PRD 且不共享 P0，就该拆。
