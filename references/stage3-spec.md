# 阶段三 · 需求定型

> 目的：把聊出来的东西变成**可验收**的东西。缺一张不算完成。
>
> **重要：下面第 1–6 节是软件形态的定型法（四张表）。**
> 文档、表格、图形、3D、音视频、资料、实物这七类形态**不适用 P0/P1/P2**——
> 它们的定型物是「产出定型卡」，见第 7 节。
> 把文档需求套进 P0 分级表，会得到一堆假的「功能」，验收时无法用。

---

## 1. 一页纸 PRD（只能一页）

```markdown
# <产品名>

## 一句话
给 <谁> 解决 <什么场景下的什么问题>，靠 <核心动作>。

## 痛点（用用户的原话，不要翻译成术语）
- "……"（引用他说的原句）

## 用户
| 角色 | 是谁 | 一天用几次 | 会不会用手机 |
|---|---|---|---|
| 主用户 | | | |
| 次要用户 | | | |

## 核心场景（写成一个故事，有时有地有人）
周三上午，<谁> 在 <哪>，要做 <什么>，现在他 <卡在哪>，用这个产品后 <变成什么样>。

## 主流程（不超过 3 步，超过就重做信息架构）
1. 打开 → 看到 <什么>
2. 点 <主按钮> → <发生什么>
3. 得到 <结果>

## MVP 范围
见「MVP 功能分级表」

## 不做清单（比做什么更重要）
- 不做 ……
- 不做 ……
```

---

## 2. MVP 功能分级

| 级别 | 定义 | 数量上限 |
|---|---|---|
| **P0** | 不做就不能用（缺了这功能，用户拿不到结果） | **≤5 个** |
| P1 | 有更好，没有也能忍 | ≤5 个 |
| P2 | 以后再说（写下来是为了不忘记，不是为了做） | 不限 |

**判定方法（一句话）**：把这个功能删掉，用户还能不能拿到他要的结果？
- 不能 → P0
- 能，但会抱怨 → P1
- 能，且不抱怨 → P2（或直接不做）

**最常见的错误**：把"登录注册、后台管理、数据统计"当 P0。
这三样在 MVP 阶段通常都是 P2——一个人用的工具不需要登录，十个用户的工具不需要后台。

---

## 3. 验收标准（写不出就删功能）

格式：**`当 <前置条件> 时，<操作>，应 <可观测的结果>`**

| 功能 | 验收标准 | 怎么测 |
|---|---|---|
| 新增记录 | 当输入框有内容时，点保存，应在 1 秒内出现在列表顶部 | 手动点一次 |
| 搜索 | 当输入"张"时，应列出所有含"张"的记录 | 输 3 个关键词 |
| 导出 | 当点导出时，应下载一个能被 Excel 打开的 csv | 打开看 |

**不合格的验收标准**（必须重写）：
- "界面美观" → 无法测
- "性能良好" → 无法测
- "支持多种格式" → 没说哪几种

---

## 4. 数据最小集（这张表决定能不能做）

只列**必须存**的字段。每多一个字段，就多一份输入负担与合规义务。

| 实体 | 字段 | 类型 | 谁填 | 必填 |
|---|---|---|---|---|
| 记录 | 标题 | 文本 | 用户 | 是 |
| 记录 | 金额 | 数字 | 用户 | 是 |
| 记录 | 时间 | 日期 | 自动 | 是 |

**三条规则**：
1. 能不存就不存（不存手机号就不用做短信、不用做隐私同意）
2. 能自动就别让用户填（时间、位置、序号）
3. 敏感字段（身份证、人脸、健康、位置）出现即触发合规工序，MVP 阶段优先去掉

---

## 5. 回读确认（最省时间的一步）

定型后，用一段话把结论复述给用户，让他挑错：

> "我理解你要的是：**给 <A>**，在 **<B 场景>** 下解决 **<C 问题>**，
> 靠 **<D 核心动作>** 实现，只做 **<P0 列表>**，
> **不做 <E/F/G>**。这样对吗？"

错的地方他会立刻说"不是，应该是……"——**这一步能省掉后面 80% 的返工**。

---

## 6. 定型后的自检

- [ ] 一句话能说清（说不清 = 还没定型）
- [ ] P0 ≤5 个
- [ ] 每个 P0 有可测的验收标准
- [ ] 有明确的不做清单
- [ ] 数据字段能覆盖主流程（走一遍，看会不会断）
- [ ] 用户确认过一遍

---

## 7. 非软件形态：产出定型卡

软件之外的一切，用同一张卡。模板：`assets/templates/产出定型卡.md`
生成：`v2p spec new --title "XX" --brief`
校验：`v2p spec check --file XX.md --form doc`

七段，缺一段不算完成：

| 段 | 要写什么 | 不写会怎样 |
|---|---|---|
| **一句话** | 给谁 + 什么场景 + 什么问题 + 靠什么动作 | 没有主轴，后面每段都各写各的 |
| **对象与用途** | 到底是什么，谁拿到后做什么动作 | 交付成"一份资料"，用户没法用 |
| **必须包含的内容** | 5–9 条内容单元，缺一条即不合格 | 交付必然缺项，且验收时无法争论 |
| **不做什么** | 明确排除的范围 | 边界无限扩张，永远做不完 |
| **验收标准** | 「当……应……」，第三人可判断 | 只能靠"我觉得不对"来验收 |
| **关键约束** | 尺寸/时间/预算/合规/工具 | 做完发现尺寸不对、超预算 |
| **深度记录** | 形态、深度等级、已覆盖维度、默认假设 | 风险被藏起来，返工无从解释 |

### 「必须包含的内容」是这张卡的核心

写法和软件的 P0 不同：**P0 是"功能"，内容是"单元"**。

| 形态 | 内容单元长什么样 |
|---|---|
| 文档 | 章节 + 每章必须回答的问题 |
| 表格 | 列 + 每列的口径定义 |
| 图形 | 画面元素 + 信息层级 |
| 3D | 部件清单 + 精度要求 |
| 音视频 | 分镜/段落 + 每段承担的信息 |
| 资料 | 目录层级 + 检索维度 |
| 实物 | BOM 条目 + 工艺要求 |

**判定方法**：这些单元能不能被**逐个勾选**？不能勾选的（"专业感""完整性"）不是内容单元，是形容词。

---

## 8. 各形态的定型检查点

定型完，按下表逐项过。任一项答"没有"，回去补问，不要进入阶段四。

| 形态 | 必过的检查点 |
|---|---|
| app | P0 ≤5、主流程 ≤3 步、数据字段能覆盖流程、不做清单非空 |
| doc | 读者能据此做的那个决定写清了、篇幅定了、模板口径确认了、禁写内容列了 |
| sheet | 一行代表什么定了、每个计算口径定了、数据入口定了、谁看看什么定了 |
| visual | 用途+尺寸定了、风格参照有了（最好是图）、交付张数定了、禁用元素列了 |
| model3d | 用途定了（看/渲染/打印/引擎/开模）、精度定了、尺寸依据有了、交付格式定了 |
| media | 平台+时长定了、素材来源定了、交付形式定了、禁出现内容列了 |
| material | 检索方式定了（怎么 3 秒找到）、公开范围定了、维护责任人定了 |
| physical | 数量级定了、硬约束列了、验收方式定了、禁区列了 |

> 这张表是**防漏清单**，不是流程。发现某项空着，回去问一句就行，不必重走四阶段。
