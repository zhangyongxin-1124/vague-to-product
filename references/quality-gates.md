# 交付质量闸门（Quality Gate）

> 这份文档只解决一个问题：**为什么需求挖对了、东西也做出来了，用户还是一眼看出「这是 AI 做的」。**
>
> 答案很少在界面上。界面只是最显眼的一层。真正露馅的是：**只有 20% 的正常路径被照顾到了，剩下 80% 的空、错、边界、兼容、并发、权限全在裸奔。**

---

## 1. 只做正常态的三个成因

不是模型懒，是三个结构性原因：

| 成因 | 表现 | 为什么会这样 |
|---|---|---|
| **演示导向** | 一屏有数据、有图、有点击态，看起来就"完成"了 | 演示和验收都靠"看一眼"，而一眼只看得到正常态 |
| **需求只说了正常路径** | 用户说"能发布岗位就行"，没说过"没人发布时怎么办" | 挖掘阶段漏了这个维度，产出阶段自然不补 |
| **改一次只改一处** | 用户说"这里不对"，就只改这里 | 局部修好、别处崩，因为没人跑回归 |

**结论**：状态与边界不是"实现细节"，是**需求的一部分**。所以它必须发生在**写第一行之前**，而不是交付前的检查。

> 后置检查能拦住 40%，前置定义能拦住 80%。这是本闸门和普通"验收清单"的根本区别。

---

## 2. 三条铁律

1. **先填状态矩阵，再动手**。矩阵填不出来，说明需求没挖到，回到阶段二，不要用"到时候再说"糊过去。
2. **阻断项不许降级**。密钥泄露、越权、重复下单、假数据上线，只有"修好"和"没做完"两种状态，没有"基本可用"。
3. **不许用"应该没问题"交付**。每条阻断项都要有一次**实际动作**作证据（点了、断网了、刷新了），不是推理出来的。

---

## 3. 状态矩阵（前置产物）

写第一行代码 / 第一段正文之前，先把这张表填满。**每一行的"用户看到什么"必须是具体的一句话，不能写"友好提示"。**

### 软件应用

| 情况 | 触发条件 | 用户看到什么 | 能做什么 |
|---|---|---|---|
| 加载中 | 首次进入 / 点按钮 / 下拉刷新 | | |
| 没有数据 | 一条都没有 / 筛选后为空 | | |
| 出错 | 请求失败 / 超时 / 无权限 | | |
| 成功 | 保存、提交、删除之后 | | |
| 不可用 | 条件不满足 | | |
| 极端量 | 1 条 / 1 万条 / 超长文本 | | |
| 素材缺失 | 图片、字体加载失败 | | |

### 非软件形态的等价物

"状态"在文档、表格、3D 里不是加载与错误，而是**完整性、缺项、超量、异常**四件事：

| 形态 | 四种情况 |
|---|---|
| 文档 | 完整 / 缺项（数据拿不到怎么标）/ 超量（篇幅超了怎么取舍）/ 异常（被质疑来源怎么答） |
| 表格 | 完整 / 空值（未填·不适用·待补要区分）/ 错误值（#N/A、除零、文本型数字）/ 超量 |
| 图形 | 完整 / 缺字（标题超长、字体缺失）/ 缩略（小尺寸是否成立）/ 异常（图加载失败） |
| 3D | 完整 / 破面 / 尺寸单位 / 超出幅面 |
| 音视频 | 完整 / 开头 / 缺素材 / 异常（字幕不同步、音乐无授权） |
| 资料 | 完整 / 缺档 / 超量（文件太多找不到）/ 过期（旧版混在新版里） |
| 实物 | 完整 / 缺料 / 超量（数量级变→工艺变）/ 不合格处置 |

> 这张表也是**挖掘工具**：填"空态说什么"时，用户往往会突然想起"对了，还有人会一次都没发过"。这就是需求被逼出来了。

## 4. 六道闸门

| 闸门 | 治什么病 | 失败的典型长相 |
|---|---|---|
| **完整态** | 只有一屏顺利的情况 | 点了没反应、列表空白、报 undefined、保存了没提示 |
| **交互** | 能用但难用 | 浮层被遮、背景乱滚、返回丢筛选、连点发三次请求 |
| **布局** | 局部正确、整体打架 | 手机横向滚动、长标题撑爆卡片、深色下看不见字 |
| **数据** | 看着正常，真数据一来就崩 | 假姓名假手机号、字段 undefined、时间差 8 小时、金额 0.30000000000000004 |
| **工程** | 本地好、换环境炸 | 密钥写在前端、构建失败、内存一路上涨、一错全白 |
| **可维护** | 改一处崩三处 | 调不存在的接口、同类页面两种写法、改坏了回不去 |

全量 65 项（软件 48 项），编号规则 `QG-<闸门号><序号>`：

- `QG-1xx` 完整态　`QG-2xx` 交互　`QG-3xx` 布局
- `QG-4xx` 数据　`QG-5xx` 工程　`QG-6xx` 可维护
- `QG-7xx` 非软件形态的等价检查

每项都写清三件事：**问什么（用户视角的现象）· 怎么验（一个具体动作）· 怎么修（一句话方案）**。

```bash
v2p gate list -f app            # 全量 48 项
v2p gate list -f doc            # 文档只出 12 项，不会问"加载态"
v2p gate list -f app -s block   # 只看阻断项
```

## 5. 按深度裁剪（别对一张通知要求 48 项）

| 挖掘深度 | 查什么 | 项数（软件） |
|---|---|---|
| D0 / D1 | 只查核心 7 项（加载·空·错·成功·禁用·防重复·密钥） | 7 |
| D2 | 全部阻断项 | 30 |
| D3 / D4 | 全量 | 48 |

判断依据沿用阶段⓿ 的五信号。**涉钱、给公众用、已上线**的，直接按 D3 全量走，不许裁。

---

## 6. 通过标准（可判定的数字）

```
阻断项未通过数 = 0          ← 硬性
提醒项未通过数 ≤ 3          ← 超出说明质量在滑坡
每条未修的提醒项写明理由    ← "没时间"不算理由
```

交付话术里必须有一句 **"我没做什么"**。把未修的提醒项写进去，用户才知道那是缺口，不是遗漏。

**禁止说法**：「基本能用」「应该没问题」「小问题不影响」。这三句出现时，说明你在替未通过的阻断项找台阶。

---

## 7. 破坏性测试：必须真的做，不能想象

AI 最容易犯的错是"推理出应该没问题"。所以闸门提供**照着点的步骤**：

```bash
v2p gate redteam -f app     # 12 步
v2p gate redteam -f doc     # 5 步
```

软件类的 12 步，普通人不看代码也能做前 8 步：

1. 断网后点主按钮
2. 详情页地址复制到无痕窗口直接打开
3. 列表滚到第 5 屏 → 进详情 → 返回
4. 输入 60 个汉字 + 超长网址 + emoji 再保存
5. 网速调慢，连点提交 3 次，数后台记录
6. 手机系统字体调到最大
7. 横屏再竖屏
8. 用另一个账号改地址里的 id 访问别人的数据
9. 系统时区改成 UTC
10. 让接口返回空数组
11. 打开控制台看红字与密钥
12. 点最后一个输入框，等键盘弹起

**判据统一**：白屏 / 没反应 / 数据错 / 文字被切 / 报错看不懂 —— 任一出现即未通过。

## 8. 静态扫描的边界（必须诚实说明）

```bash
v2p gate scan -p ./我的项目
```

扫的是**已知模式**：密钥明文、写死的假数据、过大的 z-index、写死高度、字符串解析日期、非加密外链、innerHTML 直写、SQL 拼接、小字号、残留调试输出，以及**"列表渲染了但完全没有空态/加载态处理"**。

它有三种明确局限：

| 局限 | 说明 |
|---|---|
| 启发式 | 命中不等于一定错（`height: 48px` 可能合理），没命中不等于没问题 |
| 只看文本 | 运行时才出现的竞态、内存泄漏、层级冲突扫不出来 |
| 会误报 | 扫描器把测试数据当真实假数据是常见的，需人工判断 |

所以：**scan 用来挑出该看的地方，redteam 才是判据。** 不要用"扫描通过"代替"点过一遍"。

---

## 9. 回流：填不出来的项就是新需求

闸门不是终点，是**挖掘的补充轮**。出现下面情况时，回到阶段二补问，而不是硬填：

| 现象 | 说明缺了什么 | 补问 |
|---|---|---|
| 空态写不出话 | 不知道用户第一次进来想要什么 | "第一次打开，你最想让他看到什么？" |
| 成功态想不出提示 | 不清楚这个动作的意义 | "保存完之后，他下一步该干什么？" |
| 极端量没概念 | 不知道真实规模 | "最多会有多少条？谁在用？" |
| 权限只有前端 | 没想清角色 | "有几种人用？各自能改什么？" |

这些问题的答案，往往比前面五轮问出来的更接近真需求——因为它们问的是**具体场景**，不是抽象偏好。
