# 终局交付规范（Final Delivery）

> v2.4.0 新增。回答一个问题：**需求挖掘结束之后，流程到底在哪结束？**
> 答案：在「阶段产出 B 最终产品 + 阶段产出 C 合规流程报告」两件套交付完毕的地方。
> PRD / 定型卡 / 方案对比都只是里程碑，不是终点。

---

## 1. 为什么必须加这条铁律

真实失败案例（2026-11-04，闹钟 App）：

- 用户说"我想做一个闹钟 app"→ D3 挖了 3 轮 → 交付一页纸 PRD → 流程即停。
- 用户拿到的是"需求文档"，不是"闹钟 app"。他随后不得不另起一轮对话说"把产品做出来"。

**根因**：分批深挖模式里「阶段产出 A」交付 + 回读确认，容易被执行成"本轮已完成"。
**修正**：铁律 19/20 + 本规范。回读确认通过（或默认假设兜底）后，**必须**继续走到 7.4 两件套；
唯一合法停点：用户明确说"本轮只要方案 / 先不落地"（记为"用户豁免"，写进交付说明）。

## 2. 阶段产出 B：最终产品（必交）

### 2.1 八形态最低完成定义

| 形态 | 最低完成定义 | 不合格的样子 |
|---|---|---|
| 软件（app） | 可构建 / 可运行的完整工程 + 构建说明 + 自测记录 | 原型图、PRD、功能清单、"建议你找一个开发" |
| 文档（doc） | 成稿文件（docx / pdf），可直接使用转发 | 大纲、目录、"要点梳理" |
| 表格（sheet） | 成品表：表头 + 公式 + 口径说明 + 示例行 | 字段清单、列名列表 |
| 图形（visual） | 最终格式成图（PNG / SVG / 源文件） | 文字描述、"可以找设计师画" |
| 3D（model3d） | 模型文件（STL / OBJ / STEP）+ 预览图 | 建模思路 |
| 音视频（media） | 成片（MP4）或完整可拍脚本 + 分镜 | 主题建议、内容方向 |
| 资料（material） | 完整目录 + 内容本身 + 检索方式 | 收集清单、"建议去 XX 找" |
| 实物（physical） | 可询价 BOM + 图纸 / 方案 + 验收单 | 需求描述 |

### 2.2 合规档位只改变标注，不改变交付

| 档位 | 判定 | 处理 |
|---|---|---|
| 绿灯 | 召回红线无阻断，或全部可在交付后补办 | 正常交付 |
| 黄灯 | 存在提前期长 / 主体受限的红线（如软著 30-60 工作日、类目不对个人开放） | **照常交付** + 红线写成「上架 / 经营前必须办理清单」 |
| 红牌 | 硬违法路线（涉赌 / 涉黄 / 无证经营 / 侵权核心玩法） | 交付「合法改造路线」的产品版本 + 明确告知原路线不可上线 |

**禁止行为**：
- ❌ "因为可能有合规风险，先不做了，等你确认"——黄灯不是停工理由，办证周期可与开发并行；
- ❌ "建议你先去办软著，办完再来做产品"——顺序反了，软著申请材料里就要用产品信息；
- ❌ 只交 PRD / 方案对比就说"完成"。

### 2.3 实物优先与目标形态核对（v2.5.1 新增，交付前强制执行）

真实失败案例（v2.5.0 期间）：用户明确要"跑步运动 app"，流程建完了 PWA 工程，但最终呈现的产物清单里只有 README / PRD / 合规流程报告 / 自查清单四个 .md 文档——产品本体没有作为交付物出现，用户看到的全是文档。堵法：交付前按下面四步机械核对，不过不许收口。

1. **回看目标**：圈出用户目标原话的形态名词（"我要一个 app"→`app`）。
2. **核对本体**：产物清单必须含该形态**本体实物**（对照 2.1 表"最低完成定义"列取"用户拿起来就能用"的那一件）：

| 形态 | 本体实物（产物清单里必须存在、且排第一） |
|---|---|
| 软件（app） | 可安装包（.apk / .exe / …）**或**可直接打开运行的应用入口（index.html / 可访问 PWA URL / 可导入的完整工程）——**且必须匹配用户目标设备，见下方 2.4 设备匹配表** |
| 文档（doc） | 成稿 docx / pdf 本体文件 |
| 表格（sheet） | xlsx / csv 成品表本体 |
| 图形（visual） | PNG / SVG 成图本体 |
| 3D（model3d） | STL / OBJ 模型文件本体 |
| 音视频（media） | MP4 成片本体 |
| 资料（material） | 完整资料库目录本体 |
| 实物（physical） | BOM + 图纸 / 方案包本体 |

3. **排序与呈现（v2.6.0 收紧）**：本体实物排产物清单第一项；PRD（A）/ 合规流程报告（C）/ 自查清单（D）排其后，只作附属件。**最终交付消息第一段必须回答"东西在哪、怎么打开"**（手机形态给 URL / 二维码 / 导入预览步骤 + 真机自测指引），文档列表只能排后面。
4. **判定**：产物清单里**只有 .md 文档 = 流程未完成**——禁止输出收口语、禁止说"交付完成"，回阶段④继续把本体做出来。

### 2.4 目标设备匹配（v2.6.0 新增，本体合格的第二道门）

本体存在还不够，还必须**在用户指定的目标设备上能打开**。用户原话里的设备/场景词决定判定标准：

| 用户原话出现… | 本体必须满足 | 典型不合格（=未完成） |
|---|---|---|
| 手机APP / 手机上用 / 装个APP / 掌上… | ① .apk 安装包；② 微信小程序工程（导入微信开发者工具→真机预览）；③ 已部署的移动端 Web App URL（手机浏览器/扫码即开，含 viewport 移动端布局） | PC 本地端口（localhost:xxxx）+ PC 浏览器页面；"在电脑上跑通了"的网页；未部署的纯工程目录 |
| 电脑软件 / 桌面应用 | .exe 可安装包或双击即用的可执行入口 | 只有源码目录 |
| 网页 / 网站 | 已部署 URL 或双击可开的 index.html | 只有工程源码 |
| 小程序 | 完整小程序工程（app.json / project.config.json 齐备，可导入开发者工具真机预览） | 网页版替代品 |
| （未提设备） | 按"最顺手的可用形态"交付，并在交付说明第一段写明**形态 + 打开方式** | 交付说明不写怎么打开 |

关键认知：**本地起端口跑通了 ≠ 交付了**——用户的手机永远够不着你电脑上的 localhost。要手机能用，就必须给手机能到达的入口（APK / 小程序工程 / 部署后的公网或局域网 URL）。

## 3. 阶段产出 C：合规流程报告（必附）

### 3.1 定位

让用户拿到产品的同时，明确**后续怎么走、怎么安排**——不是再问一轮问题，
而是把 `v2p plan` 已召回的红线与倒排，按「办证流程」重组成人能执行的安排。

### 3.2 五件套（缺一不合格）

1. **结论档位**：绿 / 黄 / 红 + 一句话结论（能不能上架、能不能经营、条件是什么）
2. **已触发红线清单**：引用 RFE-RL / RFE-PT 统一编码，逐条标「测试版可缓办 / 上架前必须」
3. **办证清单**：软著 / App 备案 / 隐私合规材料 / 资质许可，逐项带提前期与官方核实入口
4. **倒排周计划**：从今天到"可上架 / 可经营"，标关键路径（不可压缩项）与可并行项
5. **免责 7 条 + 知识库复核时间戳**（与 plan 报告同标准）

### 3.3 与 rfe 的衔接

- 编排路径：`v2p plan -t "..."` 已在内部单向调用 fuzzy-reverse-flow，红线 / 资源底线 / 倒排直接引用；
- 单独路径：`rfe recall -q "..." --severity redline` + `rfe doctor`（复核时间戳）；
- 模态切换（铁律 17）：进入本节即切「少问多推」，不向用户追问资质问题；
- 沉淀收口：合规报告交付后照常 `v2p settle`，把本次新确认的资质红线写回待审区。

### 3.4 报告骨架

使用 `templates/合规流程报告.md`。
